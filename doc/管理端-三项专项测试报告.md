## 四、发现的问题

### 4.1 【中】受限管理员可修改其他管理员的显示名/邮箱

- 位置：[AdminUserService.kt](file:///Users/wgp/Desktop/DentalClinic/panel/XianTong/server/src/main/kotlin/admin/service/AdminUserService.kt#L125-L144)
- 现象：`updateUser` 仅在 `roleIds != null || clinicIds != null` 时执行 `requireFullClinicScope`；只传 `displayName`/`email` 时，任意持有 `user:update` 的受限账号都能修改超管的账号资料（实测返回 200）。
- 影响：不涉及提权（不能改角色/授权/密码/状态），但属系统全局数据的跨范围写入，与“账号/角色等系统管理仅全店范围可写”的口径不一致，可用于社工/伪装。
- 建议方案（待确认）：
  1. 在 `updateUser` 开头统一 `requireFullClinicScope`，即账号资料维护一律仅超管；或
  2. 仅当目标账号与操作者共享至少一个授权门店时允许改资料，并禁止修改超管账号。
  - 推荐方案 1，实现最小、口径统一。

### 4.2 【中】C 端尾款支付接口的异常分支返回 500 序列化错误，而非约定的 404

- 位置：[UserConsumptionRoutes.kt](file:///Users/wgp/Desktop/DentalClinic/panel/XianTong/server/src/main/kotlin/user/route/UserConsumptionRoutes.kt#L85-L121)
- 现象：`call.respond(ApiResponse<Any>(...))` 无法为泛型 `Any` 生成序列化器，触发 `SerializationException`，被全局异常处理包装成 HTTP 400 `请求体解析失败: Serializer for class 'ApiResponse' is not found`。
- 影响：重复支付、无效 ID、记录不存在三类场景都返回 400 且文案错误；小程序端无法按 404 区分“已支付/不存在”，可能表现为报错或重复请求。
- 建议方案（待确认）：
  1. 将错误响应改为项目内已有的可序列化错误 DTO（如 `ApiResponse<Unit>` 或统一的 `ErrorResponse`），并为这 3 个分支补 `call.respond(HttpStatusCode.NotFound, ...)`；同时补 3 条接口测试用例。
  - 推荐方案 1。

### 4.3 【低】`PUT /api/admin/roles/{id}` 仅传 `permissionIds` 时 500（已在使用中规避）

- 位置：[AdminRoleService.kt](file:///Users/wgp/Desktop/DentalClinic/panel/XianTong/server/src/main/kotlin/admin/service/AdminRoleService.kt#L92-L95)
- 现象：`roleName` 与 `description` 同时为 null 时仍执行 `AdminRoles.update {}`，Exposed 抛出 `Can't prepare UPDATE statement without fields to update`，接口返回 500。
- 影响：仅改权限的前端调用会失败；带角色名一起提交可绕过。
- 建议方案（待确认）：仅当 `roleName != null || description != null` 时执行 UPDATE；补一条“只传 permissionIds”的用例。

## 六、结论

1. 多门店权限隔离：**通过**。列表、详情、统计、门诊下拉、跨店写入、系统管理写入均按授权门店收敛；显式传参不能越权；唯一例外是 4.1 的账号资料修改。
2. 消费尾款支付闭环：**业务链路通过**。pending 录入 → C 端可见 → 发起支付 → 落库结算（paid_at/交易号）→ 积分与会员累计发放 → 重复支付不重复结算。异常分支的状态码与响应体存在 4.2 缺陷。
3. 手机号加密存储：**通过**。历史明文自动迁移为 AES-256-GCM 密文 + HMAC 盲索引，读取按密文解密，搜索走盲索引，密文损坏时拒绝回退明文。
4. 三个问题已在确认后按推荐方案修复并回归通过，详见第七节。
