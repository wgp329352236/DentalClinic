# 归属门店移除（方案 C）迁移设计

> 目标：取消「客户只有一个归属门店」的模型，改为「客户与门店是多对多业务关系」。
> 小程序端不再让用户选择门店；管理端门店维度的客户数据改由业务事实推导。
>
> 状态：**设计稿，未实施**

---

## 1. 背景

现状里 `user.primary_clinic_id` 同时承担了三种职责：

1. C 端资料页让用户自选「归属门店」（用户视角不合理，患者属于整个医院）
2. 管理端客户列表、看板、积分商城、推荐关系的**门店数据隔离依据**
3. 首次预约时自动写入，作为「客户来自哪家店」的运营口径

单一字段无法表达「一个患者在多店就诊」。方案 C 移除该字段，改为**客户-门店关系表**，由业务事件驱动写入，管理端所有门店维度改读新表。

---

## 2. 目标模型

### 2.1 新表 `customer_clinic_relation`

```sql
CREATE TABLE IF NOT EXISTS customer_clinic_relation (
  id                 BIGSERIAL PRIMARY KEY,
  user_id            BIGINT NOT NULL,
  clinic_id          BIGINT NOT NULL,
  first_visit_at     TIMESTAMP NOT NULL DEFAULT now(),  -- 首次与本店产生业务
  last_visit_at      TIMESTAMP NOT NULL DEFAULT now(),  -- 最近一次与本店产生业务
  appointment_count  INT NOT NULL DEFAULT 0,            -- 冗余计数（可选，用于看板性能）
  consumption_count  INT NOT NULL DEFAULT 0,
  consumption_amount NUMERIC(12,2) NOT NULL DEFAULT 0,
  source             VARCHAR(20) NOT NULL DEFAULT 'appointment',
                     -- appointment / consumption / recharge / points_exchange / legacy_primary / manual
  created_at         TIMESTAMP NOT NULL DEFAULT now(),
  updated_at         TIMESTAMP NOT NULL DEFAULT now()
);

CREATE UNIQUE INDEX IF NOT EXISTS ccr_uk_user_clinic
  ON customer_clinic_relation(user_id, clinic_id);
CREATE INDEX IF NOT EXISTS ccr_idx_clinic_last
  ON customer_clinic_relation(clinic_id, last_visit_at DESC);
CREATE INDEX IF NOT EXISTS ccr_idx_user
  ON customer_clinic_relation(user_id);
```

说明：

- 唯一键 `(user_id, clinic_id)` 保证同一客户在同一门店只有一条关系
- 冗余计数列为可选优化；若看板接受实时聚合，可去掉，改为每次聚合查询

### 2.2 写入时机（事件驱动，all-or-nothing 于同一事务）

| 事件 | 写入点 | source |
|---|---|---|
| 预约创建成功 | 用户端 `AppointmentService.create` / 管理端代客预约 | `appointment` |
| 消费录入成功 | 管理端消费录入、C 端尾款支付成功 | `consumption` |
| 充值成功 | 充值回调 / 余额充值 | `recharge` |
| 积分兑换成功 | 积分商城下单 | `points_exchange` |
| 历史数据兜底 | 一次性迁移脚本 | `legacy_primary` |
| 管理端手动补录 | 新增「补录到店」动作（替代原「调整归属门店」） | `manual` |

写入口统一封装，避免散落：

```kotlin
// 建议位置：admin/service/CustomerClinicRelationService.kt
fun touch(userId: Long, clinicId: Long, source: String, at: Instant = Instant.now())
```

语义：存在则更新 `last_visit_at = GREATEST(last_visit_at, at)`、`appointment_count/consumption_count/amount` 累加；不存在则插入。

### 2.3 读取口径

| 场景 | 旧口径（primary_clinic_id） | 新口径（customer_clinic_relation） |
|---|---|---|
| 客户列表（单店管理员） | `user.primary_clinic_id = 本店` | `relation.clinic_id = 本店` 的用户，按 `last_visit_at DESC` 排序 |
| 客户详情 | 显示唯一归属门店 | 显示「关联门店列表」+ 每店首次/最近到店 |
| 客户数（本店） | `primary_clinic_id = X` | `relation.clinic_id = X` 去重用户数 |
| 新客（本店） | 注册时间在区间且归属本店 | `first_visit_at` 落在区间的用户 = 本店新客 |
| 活跃客户 | 区间内有预约/消费且归属本店 | `last_visit_at` 落在区间的用户 |
| 门店对比 | 按归属门店分组 | 按 relation 分组（同一客户可计入多店） |
| 推荐关系 | `referee.primary_clinic_id` | 被推荐人 `first_visit_at` 最早的那条关系的门店 |
| 积分兑换订单 | 按客户归属门店统计 | 订单表无 `clinic_id`；改为按核销门店统计，或记为「未归属」 |

> 注意：「新客」的语义会从「注册新客」变成「到店新客」，看板数字会跳变，需要业务确认（见第 7 节）。

### 2.4 权限校验

`ClinicScopeGuard.assertUserInScope(userId, scope)` 改为：

```sql
SELECT 1 FROM customer_clinic_relation
WHERE user_id = :userId AND clinic_id IN (:scopeClinicIds)
LIMIT 1
```

- 单店管理员：只能看/操作与本店有业务关系的客户
- `clinic:data:all` 账号：保持全量可见
- `scopeUserIds(scope)` 改为从 relation 取用户集合

## 3. 接口变更

### 3.1 管理端

| 接口 | 变更 |
|---|---|
| `GET /api/admin/customers` | `clinicId` 语义变为「关联门店」；响应增加 `clinicIds: [Long]`、`lastVisitAt` |
| `GET /api/admin/customers/{id}` | 删除 `primaryClinicId`，新增 `clinics: [{clinicId, clinicName, firstVisitAt, lastVisitAt}]` |
| `PUT /api/admin/customers/{id}/clinic` | **删除** |
| 新增 `POST /api/admin/customers/{id}/clinics` | 手动补录到店（需审计日志），替代原调整归属 |
| 看板类接口 | 指标口径按 2.3 重算，字段名保持不变以避免前端大改 |

### 3.2 小程序端

| 接口 | 变更 |
|---|---|
| `GET /api/v1/profile/me` | 删除 `primaryClinicId` |
| `PUT /api/v1/profile/me` | 删除 `primaryClinicId` 入参 |
| `POST /api/v1/points/profile-complete-reward` | 不再校验归属门店 |

### 3.3 兼容性（关键）

后端 DTO 删除字段后，**旧版小程序**仍会传 `primaryClinicId`：

- 若 `kotlinx.serialization` 未开启 `ignoreUnknownKeys`，旧客户端会收到 400「请求参数格式不正确」
- 处理方式二选一：
  1. **推荐**：先发布小程序新版本（可灰度），确认覆盖率后后端再删字段
  2. 过渡期在 `UpdateProfileRequest` 上单独开启 `ignoreUnknownKeys = true`，下一版本再删

管理端与后端同仓发布，无兼容问题。

## 4. 迁移步骤

### 阶段 0：备份

```bash
pg_dump -Fc -f backup_before_ccr_$(date +%F).dump "$PGDATABASE"
```

### 阶段 1：建表

执行 2.1 的 DDL。此阶段对现有功能零影响，可随时 `DROP TABLE` 回滚。

### 阶段 2：历史数据回填

```sql
-- 2.1 预约（排除已取消，状态枚举按实际调整）
INSERT INTO customer_clinic_relation
  (user_id, clinic_id, first_visit_at, last_visit_at, appointment_count, source)
SELECT user_id, clinic_id, MIN(created_at), MAX(created_at), COUNT(*), 'appointment'
FROM appointment
WHERE status <> 'cancelled'
GROUP BY user_id, clinic_id
ON CONFLICT (user_id, clinic_id) DO UPDATE SET
  first_visit_at    = LEAST(customer_clinic_relation.first_visit_at, EXCLUDED.first_visit_at),
  last_visit_at     = GREATEST(customer_clinic_relation.last_visit_at, EXCLUDED.last_visit_at),
  appointment_count = customer_clinic_relation.appointment_count + EXCLUDED.appointment_count,
  updated_at        = now();

-- 2.2 消费
INSERT INTO customer_clinic_relation
  (user_id, clinic_id, first_visit_at, last_visit_at, consumption_count, consumption_amount, source)
SELECT user_id, clinic_id, MIN(created_at), MAX(created_at), COUNT(*), SUM(amount), 'consumption'
FROM consumption_record
WHERE status = 'success'
GROUP BY user_id, clinic_id
ON CONFLICT (user_id, clinic_id) DO UPDATE SET
  first_visit_at     = LEAST(customer_clinic_relation.first_visit_at, EXCLUDED.first_visit_at),
  last_visit_at      = GREATEST(customer_clinic_relation.last_visit_at, EXCLUDED.last_visit_at),
  consumption_count  = customer_clinic_relation.consumption_count + EXCLUDED.consumption_count,
  consumption_amount = customer_clinic_relation.consumption_amount + EXCLUDED.consumption_amount,
  updated_at         = now();

-- 2.3 充值
INSERT INTO customer_clinic_relation
  (user_id, clinic_id, first_visit_at, last_visit_at, source)
SELECT user_id, clinic_id, MIN(created_at), MAX(created_at), 'recharge'
FROM recharge_record
WHERE status = 'success'
GROUP BY user_id, clinic_id
ON CONFLICT (user_id, clinic_id) DO UPDATE SET
  first_visit_at = LEAST(customer_clinic_relation.first_visit_at, EXCLUDED.first_visit_at),
  last_visit_at  = GREATEST(customer_clinic_relation.last_visit_at, EXCLUDED.last_visit_at),
  updated_at     = now();

-- 2.4 历史归属兜底：只有归属门店但无任何业务记录的客户
INSERT INTO customer_clinic_relation
  (user_id, clinic_id, first_visit_at, last_visit_at, source)
SELECT id, primary_clinic_id, created_at, created_at, 'legacy_primary'
FROM "user"
WHERE primary_clinic_id IS NOT NULL
ON CONFLICT (user_id, clinic_id) DO NOTHING;
```

校验：

```sql
-- 每个有归属门店的用户，在新表至少有一条关系（数量应为 0）
SELECT count(*) FROM "user" u
WHERE u.primary_clinic_id IS NOT NULL
  AND NOT EXISTS (SELECT 1 FROM customer_clinic_relation r WHERE r.user_id = u.id);
```

### 阶段 3：双写 + 双读（后端上线，管理端不变）

- 所有业务事件增加 `touch()` 写入（同一事务）
- 管理端接口仍读 `primary_clinic_id`，行为不变
- 观察期核对：随机抽取客户，对比旧归属门店与新关系表是否一致

回滚：回滚代码即可，新表保留无害。

### 阶段 4：切换读口径

- `ClinicScopeGuard`、客户列表/详情、看板、推荐、积分商城全部改读 relation
- 管理端同步发布（列名改「关联门店」、删除「调整归属门店」弹窗）
- 小程序发布新版本（去掉门店 picker）

回滚：保留旧列与旧查询分支，用配置开关 `customer.attribution.mode=legacy|relation` 一键切回，观察 1~2 周后再移除。

### 阶段 5：清理

```sql
ALTER TABLE "user" DROP COLUMN IF EXISTS primary_clinic_id;
```

同步删除 `Users.primaryClinicId`、所有 DTO 字段与死代码。

## 7. 验收清单

1. 单店管理员 A：只能看到与 A 有预约/消费/充值记录的客户；查询只在 B 有记录的客户 → 403/空列表
2. 跨店客户：在 A、B 两个账号下都可见；详情展示两条门店关系及各自首次/最近到店
3. 客户列表排序与筛选按 `last_visit_at` 生效
4. 看板：本店客户数、新客数、活跃数与 SQL 对账一致
5. 小程序：资料页无「归属门店」；保存成功；完善资料积分可正常领取（无门店用户也能领）
6. 旧版小程序（未升级）调用 `PUT /profile/me` 不报 400（按 3.3 的兼容方案验证）
7. 管理端无「调整归属门店」入口；新增补录到店写入审计日志
8. 门店数据隔离专项回归：跨门店客户/预约/消费/充值/看板全部通过

## 8. 风险与待确认

| 风险 | 说明 | 处置 |
|---|---|---|
| 新客口径跳变 | 看板数字与历史不可比 | 上线前与业务确认并在后台标注口径变更 |
| 占比类图表失真 | 客户可计入多店，合计大于总数 | 门店对比改为「各店独立计数」，不做占比 |
| 从未到店客户不可见 | 仅注册未消费用户无门店归属 | 需要时可让运营通过补录到店手动关联 |
| 积分兑换订单无门店 | 表结构无 `clinic_id` | 按核销门店统计，或标记「未归属」 |
| 列表查询性能 | 客户列表改为 join 去重 | 依赖 `ccr_idx_clinic_last`，大数据量再考虑物化视图 |
| 双写一致性 | 事件写入失败会漏关系 | 与业务写同事务；另加重跑脚本按预约/消费补齐 |
| 审计能力 | 原调整归属有审计日志 | 新增补录接口必须写审计日志 |
| 数据不可逆 | 删列后无法恢复归属 | 阶段 5 前保留备份与旧列 ≥ 1~2 周 |
